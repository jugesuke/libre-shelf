# 確認

元に戻せない操作の前に、本当に実行してよいかを確認する方法です。[ダイアログ](?path=/docs/ui-dialog--docs)で出します。ブラウザの `confirm()` は使いません。

<Canvas of={ConfirmStories.DeleteOrder} />

## いつ確認するか

削除、取り消し、破棄など、実行すると元に戻せない操作の前に確認します。

## 構成

| 部分 | 書くこと | 例 |
|---|---|---|
| 見出し | 「\{対象\}の\{操作\}」 | 発注の削除 |
| 本文 | 「以下の\{対象\}を\{操作\}しますか？　この操作は元に戻せません。」 | 以下の発注を削除しますか？　この操作は元に戻せません。 |
| 対象 | 人が見て分かる項目（名前、日時、金額など）。ID は使わない | 商品名「みほん同人誌」、注文数量 100、注文日 2026/11/01 |
| 注意事項 | 操作で失われるものなど、あれば警告の[アラート](?path=/docs/ui-alert--docs)で書く | この即売会の会計とレジ金の記録が、すべて失われます。 |
| ボタン | 左に「やめる」、右に実際に起きること | やめる、削除 |

## ボタンの言葉

- 閉じるボタンは「やめる」にする。
- 確定のボタンは実際に起きることを書く（「削除」「取り消す」「破棄する」）。「OK」「はい」は使わない。
- 確定のボタンは destructive にする。

<Canvas of={ConfirmStories.CancelTransaction} />

### なぜ「キャンセル」を使わないのか

「キャンセル」と「取り消す」は、どちらも「やめる」と読めます。並べると、どちらを押すと操作が取り消されるのかが分かりません。

## 影響が大きいときの強い確認

即売会のセッションの破棄のように、まとまった記録が失われる操作では、操作の名前を入力するまで確定のボタンを押せないようにします。入力させる言葉は、見出しの「\{操作\}」と同じにします（セッションの破棄なら「破棄」）。確定のボタンと違う操作の言葉を入力させると、何を実行するのかが分かりにくくなるためです。

<Canvas of={ConfirmStories.StrongConfirmByTyping} />

### なぜチェックボックスではないのか

チェックボックスは内容を確認せずにチェックを入れる流れ作業になりやすいためです。

## 最初のフォーカス

確認ダイアログを開いたら、最初のフォーカスを「やめる」に置きます。いちばん害の少ない操作に、最初のフォーカスを置くためです。

## チェックリスト

- [ ] ブラウザの `confirm()` を使っていない。
- [ ] 対象をID ではなく、人が見て分かる項目で示している。
- [ ] 閉じるボタンが「やめる」、確定のボタンが実際に起きることになっている。
- [ ] 最初のフォーカスが「やめる」にある。
